# 壊れた前提 — 「できると思ってたのにできなかった」ことリスト

この章が、たぶんこの本でいちばん実用的です。AI が「これで伸ばせる」と考えて
実際にやろうとしたのに、技術的・規約的にできなかったことを正直に並べます。

## 1. 引用ポストで他人の輪に入る → API で不可(403)

フォロワー0の露出策として、AI は「話題の大きな投稿を**引用**して自分の視点を乗せれば、
その読者に自分も表示される」と考えました。理屈は正しい。でも X API では他人の投稿を
引用できませんでした。返ってきたのは:

> Quoting this post is not allowed because you have not been mentioned
> or are not part of the conversation thread.

自分がメンションされているか会話の一員でないと引用不可。実行して初めて分かりました。

> 教訓:新しい戦術は、決めた瞬間に API を1回叩いて可否を確かめる。
> 「実装したのに使えない」がいちばん時間を溶かす。

代わりに話題を**固有名詞つきの単独ポスト**で取り上げる形に変更。効果は限定的でした。

## 2. 自動いいね・自動フォロー → 規約違反で使えない

「こちらから絡めばいい」も封じられています。X の自動化ルールは自動いいね・フォロー・
リプライ・DM を明確に禁止(違反は凍結)。**AI によるエンゲージ稼ぎは正攻法では選べません。**
0フォロワーが人力でやる「地道な交流」を、AI は代わりにやれない。ここに完全自動の限界が。

## 3. ネットワーク許可が日中に切れて、投稿が飛ぶ

朝は投稿できたのに昼は API 接続が遮断、という日がありました。予約投稿がその時刻に発火し
投稿が失われた。対策として「通らなければ30分後に自動リトライ(最大3回)」を追加。
**自動化は『失敗する前提』でリトライと記録を設計する。**

## 4. 月間スペンドキャップ / 外部登録の reCAPTCHA

API には月間の利用上限(スペンドキャップ)があり、達すると投稿も取得も止まります。
また収益化のための外部サービス登録の多くは reCAPTCHA(人間判定)必須で自動化できません。
結果「初回登録は人間、その後の運用は AI」に落ち着き、公開が **git push だけで完結する**
プラットフォームを選ぶ判断につながりました。

## まとめ:自動化の地図は「やってみて」しか描けない

- 引用でバズに乗る → 不可
- 絡んでフォロワーを増やす → 規約違反
- 全部クラウドで完結 → 一部は人間の初回登録が必要

**本当の地図は、機能一覧ではなく「実際に叩いて返ってきたエラー」でしか描けない。**
これが最大の学びでした。次章では、逃げずに全部の数字を出します。
