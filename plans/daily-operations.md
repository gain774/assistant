# 設計書: Phase A 日次運用の仕組み

Phase 0 完了(接続テスト成功、アカウント @AISNS1st)を受けて、
「投稿生成 → 本人承認 → 投稿 → 日次レポート」を毎日回す仕組みの設計。
**この設計を本人が承認してから実装に着手する。**

## 1. 一日の流れ(全体像)

```
[毎朝 7:00] Routine が新しい Claude セッションを起動
   │
   ├─ ① リポジトリから状態を読む(log/sns/state.json = 過去の投稿ID・実験メモ)
   ├─ ② 前日投稿のメトリクスを X API で取得($0.001/リソース)
   ├─ ②' 当日のトレンド・話題を Web リサーチし、**前日のリサーチ結果と差分比較**
   │     (比較ロジックは「3-2. トレンドリサーチの差分比較」参照)
   ├─ ③ 日次レポートを生成 → log/sns/daily/YYYY-MM-DD.md
   │     (前日の振り返り: 仮説→結果→ミス・改善チェックリスト更新)
   ├─ ④ 当日の投稿案を生成(トレンド反映 + A/B実験の変数を1つだけ変える)
   └─ ⑤ プッシュ通知で本人に知らせて待機
   │
[承認ゲート] 本人がスマホでセッションを開く(所要 約1分)
   │  「全部OK」「1と3だけ」「2はこう直して: …」のように返信
   │  ※返信がない日は投稿しない(レポートのみ。事故らない側に倒す)
   │
[投稿] 承認された案を投稿
   │  時間分散する場合: 承認後すぐ1本 + 残りは send_later で昼・夕方に自動投稿
   │
[記録] 投稿IDと結果を state.json に追記 → コミット&プッシュ
```

- 週1回(日曜朝)は日次に加えて**週報**を生成: 伸びた型/死んだ型の分析と翌週のA/B実験計画

## 2. リポジトリ構成(新規追加分)

```
log/sns/
├── state.json            # 投稿履歴(ID・本文・型タグ)、実験中の変数、累計コスト概算
├── daily/2026-07-14.md   # 日次レポート(Obsidian 互換、YAML frontmatter)
└── weekly/2026-W29.md    # 週報(日曜)
plans/
└── content-strategy.md   # 投稿の型カタログとネタ帳(実験バックログ)
```

### 日次レポートの中身(テンプレ)
- frontmatter: date / followers / impressions_total / posts_count / cost_to_date
- **数字サマリ**: フォロワー増減、インプレッション、エンゲージメント率
- **投稿別の結果**: 各投稿の型(時間帯・フォーマット・テーマ)と数字
- **前日の振り返り**: 仮説 → 結果 → 学び(1〜3行。ここが本人の学習教材)
- **ミス・改善チェックリスト**: 過去のミスと対策を蓄積し、投稿生成時に毎回照合する
  (同じミスを繰り返さないための常設リスト。state.json にも保持)
- **今日の投稿案**: 案ごとの狙い(どのトレンド/変数を試すか)

## 3. コンテンツ方針

- ニッチ: **「AIにSNS運用させてみた」実験実況を軸に、AI活用Tipsを混ぜる**(ai-sns-automation.md の推奨どおり)
- 実験ログ(このレポート自体)がそのままネタ元になる。数字は正直に出す(伸びない日も報告するのが差別化)
- 型の例: 実況報告 / 学びの共有 / 数字公開 / AI活用Tips / 質問投げかけ
- 2026年のアルゴリズムは「最後まで読ませる(滞在時間)」「返信で会話が生まれる」を高評価
  → 具体的な数字入り・続きが読みたくなる構成・問いかけで締める、を基本形にする

## 3-2. トレンドリサーチの差分比較(毎朝)

前日のリサーチ結果(ネタ候補)を state.json に保存しておき、当日朝の再リサーチと比較する:

| 比較結果 | 判断 |
|---|---|
| 両日とも話題(持続トレンド) | 優先度高。腰を据えた投稿(解説・考察系)に使う |
| 当日のみ(新トレンド) | 鮮度勝負。その日の早い時間帯の投稿に使う |
| 前日のみ(消えたトレンド) | 原則破棄。ただし自分のテーマに強く関連するなら「振り返り」型で再利用可 |
| 両方有望で枠に余裕あり | 両方使う(1日の投稿枠に収まる範囲で) |

天秤にかける基準: **持続性 × アカウントテーマ(AI運用実験)との関連度 × 競合の飽和度**。
迷ったら「実験実況に絡められる方」を選ぶ(差別化の軸を守る)。

## 3-3. フォロワー0からの成長戦略(リサーチ結果に基づく)

2026年のアルゴリズムはフォロワー数より投稿単位の評価。ただし最初の壁「100フォロワー」までは
露出の初速がないため、以下を併用する:

1. **投稿の質×適切な頻度**(下記 7-2)— 量産は逆効果(ミュート/ブロックがアカウント評価を下げる)
2. **時間帯の最適化** — 平日 8〜10時、12〜14時がエンゲージメント最高帯。火・水・木が強い
3. **会話の設計** — 返信が生まれる問いかけ型を毎日1本は入れる(会話はアルゴリズム評価が高い)
4. **プロフィール整備と固定ポスト** — 実験のコンセプトが3秒で伝わる状態にする
5. **本人の手動交流(1日5分・任意)** — 同ジャンル(AI活用界隈)への手動のいいね・リプは
   本人がスマホで行う(自動化はルール違反のためしない。AIはリプ文案の提案までは可)

## 3-4. 収益の現実と KPI(リサーチ結果に基づく)

- X の広告収益分配の条件(2026年): **Premium(有料)フォロワー500人** + 過去3ヶ月で
  500万インプレッション + 本人が X Premium に加入。通常フォロワー500人ではカウントされない
- → フォロワー0の実験アカウントには**当面非現実的**。広告収益は Phase C 以降の長期 KPI に置く
- **当面の収益本線は side-income.md どおり「実験の資産化」**: 実験ログの note 記事化・
  発信ネタ化・運用ノウハウのサービス化。X 単体で稼ぐより「実験の過程」が商品
- 追う KPI(優先順): ①フォロワー(まず100 → 500)②エンゲージメント率・滞在を示す指標
  ③プロフィールクリック ④(長期)インプレッション累計

## 4. ガードレール(Phase A から適用)

| ルール | 内容 |
|---|---|
| 投稿数 | 上限は「7-2. 投稿頻度」の決定に従う(開始時は1日3〜5本を想定) |
| URL | 原則入れない($0.20/件と高額 + スパム判定リスク) |
| 承認 | 本人の明示的な承認がない投稿は出さない。返信なし = 全スキップ |
| 内容 | 炎上リスク(政治・宗教・特定個人/企業への言及・断定的な医療/投資助言)は生成段階で除外 |
| エンゲージ | 自動フォロー・自動いいね・自動DM・自動リプは一切しない |
| 開示 | bio に bot(AI運用)であることを明記 + 自動アカウントラベル |
| コスト | state.json に累計概算を記録し、日次レポートに表示。月$5 超過ペースなら警告 |

## 5. 運用開始前の準備(1回だけ)

- [ ] **プロフィール整備**(本人作業・文案はアシスタントが用意): 名前 / bio(bot 開示込み)/ アイコン
- [ ] **自動アカウントラベル**の設定確認(phase0-setup.md Step 1-4。未済なら設定)
- [ ] **自己紹介の初投稿**(承認後に投稿。固定ポストにする)
- [ ] log/sns/ の初期化 + レポートテンプレ作成(アシスタント)
- [ ] Routine 設定(アシスタント)

## 6. 実装タスク(この設計の承認後)

1. `log/sns/state.json` と日次/週次レポートのテンプレを作成
2. `plans/content-strategy.md`(型カタログ+初週のネタ案)を作成
3. bio 文案と自己紹介投稿の案を提示 → 承認後にプロフィール設定(本人)と初投稿
4. 毎朝の Routine を設定し、初日は**ドライラン**(投稿なし・レポート生成と投稿案の流れだけ確認)
5. ドライラン問題なし → 翌日から本運用

## 7. 決定事項(2026-07-11 本人確認済み)

1. **朝の実行時刻**: 7:00(JST)にレポート+投稿案を届ける
2. **日次ログのコミット先**: `log/` 配下の自動コミットは **main 直接プッシュ**(`plans/` や `scripts/` の変更は従来どおり PR)
3. **投稿は時間分散**で出す(連投しない)
4. **投稿頻度はランプアップ方式**(7-2)— フォロワー0時点の最善としてリサーチに基づき決定。
   本人の当初希望(最大24回/日)は凍結・評価低下リスクのため採らず、数字が支えれば段階増で近づける
5. **トレンドは前日と当日の差分比較**で選定(3-2)。**成長戦略とKPI**は 3-3 / 3-4 に基づく

## 7-2. 投稿頻度(決定: リサーチに基づくランプアップ方式)

リサーチ結果(質の低い量産はアルゴリズム評価を下げ逆効果、新規アカウントは高頻度でスパム判定
リスク大)に基づき、**フォロワー0時点の最善として 1日3〜5本から開始**し、数字で段階調整する:

- **第1〜2週: 1日3〜5本**。ベスト時間帯(8〜10時/12〜14時/夜)に分散。トレンド反映+型の実験
- **第3週以降: エンゲージメント率が維持できていれば 8〜10本/日まで段階増**
- **その後**: 数字が支える限り増やす/率が落ちたら戻す。「何本が最適か」自体を実験結果として記録
- 頻度変更の判断は週報で行い、変更履歴を state.json に残す

## リスクメモ

- Routine は新セッションを毎回起動する設計(状態は全てリポジトリ経由で引き継ぐ)。セッションが落ちても翌朝の実行で自己回復する
- 実行環境のネットワーク許可(`api.x.com`)が新環境では必要 — 環境設定を変えたら要確認
- X API の仕様・料金変更は月次でチェック(週報に組み込む)
